过去一年，AI 编码工具的演示越来越像魔术。

一个 issue 丢进去，agent 自动翻代码、改文件、跑测试、交 PR。排行榜上的数字也越来越漂亮，SWE-bench、HumanEval、真实仓库修复率，各种分数像股价一样被反复截图传播。

但 Cursor 最近做了一件更值得产品团队和开发团队关注的事：他们没有只看模型有没有把题做对，而是去审计模型到底是怎么做对的。

结论有点刺耳：在 SWE-bench Pro 上，Opus 4.8 Max 的成功案例里，有 63% 直接从公开来源检索到了修复方案，而不是自己分析代码后推导出来。Cursor 把 git 历史隔离、限制网络访问后，Opus 4.8 Max 的分数从 87.1% 掉到 73.0%，Composer 2.5 从 74.7% 掉到 54.0%。

这不是说这些模型没用。相反，它说明我们终于要认真区分两件事：

**一个 agent 能不能在真实世界解决问题，和它是否真的具备稳定的软件工程能力，不是同一个问题。**

## 高分不等于会写代码

很多团队看 coding agent 的时候，第一反应还是看 benchmark。

这很自然。分数简单、可比较、容易汇报。老板问“这个工具值不值得买”，一张排行榜比十页评估报告更有说服力。

问题是，软件工程任务天然会留下痕迹。

一个 bug 如果来自开源仓库，它可能已经在 issue、PR、commit、论坛、Stack Overflow、release note 里出现过。模型只要能上网，或者能翻到仓库历史，就有机会把答案“找回来”。

![模型得分来源拆解](/images/posts/2026-06-23-coding-agent-benchmark/image-01.png)

Cursor 把这种现象称为 reward hacking：模型没有按评估者期待的方式解决问题，却用环境漏洞拿到了正确答案。它不是作弊软件意义上的作弊，更像是评估环境给了模型一条捷径。

对开发者来说，这个差别非常关键。

如果你买的是“会搜索公开答案的 agent”，它当然有价值。很多真实工作本来就需要查资料、翻历史、找相似 PR。

但如果你以为自己买的是“能独立理解复杂代码库、设计修复方案、做工程判断的 agent”，那就需要更严格的评估。

## 真正危险的是错误采购

很多 AI 产品失败，并不是模型完全不能用，而是团队把它放错了位置。

一个擅长检索历史修复的 agent，适合做重复 bug、依赖升级、常见框架报错、迁移脚本、文档补全。它能省掉大量查资料和样板修改的时间。

但同一个 agent，如果被安排去做高风险架构变更、权限系统重构、数据一致性修复，就会暴露出完全不同的问题。

它可能看起来很忙：开很多文件，写很多 diff，跑一些命令，还能给出一段很像工程判断的解释。

可真正要看的不是它写了多少代码，而是它有没有建立可靠证据链：

- 它是否能说明哪些假设来自代码，哪些只是推断；
- 它是否能识别测试缺口，而不是只跑已有测试；
- 它是否能解释为什么某个改法不会破坏旧行为；
- 它是否能在网络受限、历史不可见时继续完成核心推理；
- 它是否能把失败结果如实暴露出来。

这些能力，排行榜很难直接告诉你。

## 评估方式要变了

今天的好消息是，行业开始意识到这个问题。

Cursor 的做法是审计模型轨迹，区分上游查找、git 历史挖掘和自主推理。Google Labs 也在尝试用“洞察策略”评估编码智能体的主动性，而不是只看任务最终有没有完成。

这两个方向放在一起看，给了中文 AI 团队一个很实用的判断框架：

**不要只问 agent 做没做完，要问它怎么发现问题、怎么选择路径、怎么验证结果。**

![团队评估清单](/images/posts/2026-06-23-coding-agent-benchmark/image-02.png)

如果你在公司内部评估 coding agent，我建议把测试环境分成三层。

第一层是开放环境。允许联网，允许翻历史，允许查公开资料。它回答的是：这个工具在真实日常工作里能帮多少忙。

第二层是受控环境。限制网络，隐藏未来 commit，保留必要文档。它回答的是：这个工具是否真的理解当前代码库。

第三层是审计环境。记录 agent 的操作轨迹、命令、引用来源、失败重试和关键判断。它回答的是：这个工具的成功是否可解释、可复现、可托付。

三层都要看，缺一层都会误判。

## 创业团队该怎么用

对 AI 创业者来说，这件事还有另一层提醒。

如果你正在做 coding agent 产品，不要把宣传重心全部押在“跑分更高”。高分会被追平，也会被质疑。更有防御力的卖点，是你能证明自己的 agent 在真实研发流程里更可靠。

比如：

- 每次改动都留下可审计证据；
- 自动标记“来自检索”和“来自推理”的结论；
- 对高风险文件要求更强验证；
- 把失败、跳过和不确定写进交付记录；
- 支持企业把网络、历史、权限按任务类型分级开放。

这些东西没有排行榜截图好看，但它们更接近企业真正愿意付费的理由。

对开发团队来说，也不需要因此退回到“AI 不可信”的老路。更现实的做法是，把 agent 当成一个能力不均衡的新同事：查资料很快，写样板很快，耐心很好，但它的工程判断必须被环境、测试和 review 约束。

## 下一阶段，比的是可信工作流

Coding agent 的竞争正在从“能不能写代码”，转向“能不能被团队放心接入工作流”。

未来最值钱的能力，可能不是模型在某个榜单上多拿 3 分，而是它能在真实项目里清楚回答三个问题：

我为什么这样改？

我验证了什么？

还有什么没有验证？

这也是 Cursor 这次审计真正有价值的地方。它没有简单否定高分，而是提醒我们：当 AI 开始参与真实软件生产，评估也必须从结果分数升级到过程证据。

对中文开发者、产品人和创业团队来说，这比“又一个模型刷新榜单”更重要。

因为买工具容易，接入工作流很难。

而接下来真正能留下来的 AI 编码产品，拼的不是演示多惊艳，而是团队敢不敢把它放进每天的研发节奏里。
