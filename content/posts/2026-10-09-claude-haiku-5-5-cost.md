Anthropic 在 10 月 7 日发布 Claude Haiku 5.5，面向摘要、分类、数据库查询、压缩和 Agent 子任务等高频工作。对开发者来说，最醒目的变化是：输入价格从 Haiku 4.5 的每百万 token 1 美元降到 0.10 美元（提示不超过 10 万 token 时）。

这不是把整个 AI 账单自动打九折。Haiku 5.5 的每任务 token 使用量也有变化，长提示还会进入更高价格档。真正受影响的，是需要在成本、速度和结果质量之间做选择的产品与平台团队：现在可以把更多窄任务纳入模型路由候选，但是否换用，要用自己的流量验证。

## 先看懂这次“降价”改了什么

Anthropic 将 Haiku 5.5 定位为高吞吐、成本敏感型任务模型，并称其在标准速度下是目前最快的 Claude 模型。官方给出的 API 价格按每百万 token 计：输入 0.10 美元、输出 0.50 美元；提示超过 10 万 token 的输入和输出价格分别为 0.50 美元和 2.50 美元。

相比 Haiku 4.5，前 10 万 token 档位的输入和输出单价都低 90%。但 Anthropic 也说明，新模型采用更新的 tokenizer，每个任务会略多消耗 token；其“平均运行成本约低 75%”是基于模型版本间任务用量变化后的估算，而不是每个客户账单都能省 75%。

| 项目 | Haiku 5.5 | Haiku 4.5 |
| --- | ---: | ---: |
| 输入（每百万 token，提示 ≤100K） | $0.10 | $1.00 |
| 输出（每百万 token，提示 ≤100K） | $0.50 | $5.00 |
| 超过 100K 提示的输入 | $0.50 | 需按平台价格核对 |

长上下文还有一个容易漏看的边界：超过 10 万 token 后，Haiku 5.5 的输入、输出单价变成前一档的 5 倍。对于大量塞入长文档、代码库或历史对话的请求，不能只看首页上的低价。

## 这更像一个任务分工变化

Haiku 5.5 的价值不只是“更便宜的聊天模型”，而是让产品团队重新评估哪些环节可以拆成可控的小任务。Anthropic 举的方向包括摘要、压缩、数据库查询、分类、在线客服和浏览器操作；它也建议把 Haiku 作为较大模型的编码子 Agent，处理范围明确的短步骤。

Anthropic 公布的测试中，Haiku 5.5 在 OSWorld 2.1 离线子集得分 72.4%，Haiku 4.5 为 15.7%；在 Terminal-Bench 4.0 上分别为 39.2% 和 0%。这些是厂商按自身评测口径报告的结果，不能直接等同于你的浏览器自动化成功率或真实代码任务通过率。

因此，模型路由不应只按输入单价排队。一个便宜模型如果需要更多轮重试、输出更长，或者误判后触发人工复核，单任务成本可能反而上升。反过来，对格式固定、可抽检的分类和提取任务，即使质量只相近，成本与响应速度改善也可能很有价值。

可以先用一个固定用量的例子理解价格差：假设每次任务消耗 2,000 个输入 token 和 500 个输出 token，不计缓存、批处理、工具调用和重试，那么按 Haiku 4.5 的公开单价计算，每次约 0.0045 美元；按 Haiku 5.5 在 10 万 token 内的公开单价计算，每次约 0.00045 美元。这个例子只是把 token 数固定后的账面比较，不是生产承诺。真实任务会受到新 tokenizer、提示长度、输出长度、缓存命中和失败重试影响，所以要用自己的流量重新测。

还要把“约低 75%”放在正确的位置：这是 Anthropic 根据模型之间任务用量变化给出的平均运行成本估算。它不是 token 单价降幅，也不代表每种任务都会少花四分之三。团队若要把它变成自己的预算判断，应先抽取一批代表性请求，保留原模型与 Haiku 5.5 的输入、输出 token、工具调用和重试记录，再按通过验收的结果计算总成本。这样才能知道节省来自低单价、较少人工处理，还是更快完成。

## 先挑三类任务做小流量对照

第一类是结果容易判定的短任务，例如意图分类、字段抽取、工单分流。先保留现有模型作对照，固定输入样本和输出 schema，重点测准确率、漏判率和每千条人工复核量。

第二类是 Agent 中可独立验收的子步骤，例如从材料中找一项数字、生成短摘要或压缩上下文。把它作为子 Agent，而不是直接接管整个复杂流程；记录它是否一次完成、触发了几次工具调用、主 Agent 是否需要重做。

第三类是有明确延迟预算的在线交互，如客服建议或网页检索。测端到端 P50/P95 延迟和超时率，不要只比较模型吐 token 的速度。网络、首 token、工具等待和重试都会影响用户实际等待时间。


建议至少留存这几项：

- 每个通过验收任务的总费用，而非单看每百万 token 单价；
- 首次通过率、最终通过率，以及人工返工时间；
- 输入长度分布，尤其是超过 10 万 token 的比例；
- 平均输出 token、重试次数、工具调用数和 P95 完成时间。

对照实验开始前，还应先写下停止条件。比如，分类任务的精确率或召回率低于现有模型多少就回退；客服建议出现什么类型的错误必须人工确认；Agent 子步骤超过几轮仍未完成就交还主模型。指标要按任务设置，不能用一个总体平均分掩盖某类高风险失败。样本中应包含常见请求、边界输入和历史失败案例，并避免把含有个人信息或商业秘密的原始内容直接送入未经批准的测试环境。

流量切分也要可比：在同一时间窗口、相同输入版本和相同工具权限下分配请求，记录模型版本、effort 设置和提示词哈希。先以影子流量比较答案质量，不立即改变用户看到的结果；确认差异可接受后，再从低比例流量开始。若新模型的通过率下降，先区分是模型能力、提示词适配、schema 约束还是工具链导致，再决定修提示、加校验或回退，避免只根据一次成功演示扩大切流。

最后把收益按“每个合格结果”核算：模型账单、重试与工具费用，加上抽检和人工返工时间。对于人工复核特别昂贵的任务，质量下降几个百分点就可能抵消 token 价格优势；对于可自动判错、失败后容易回退的窄任务，即便省钱幅度没有达到厂商的平均估算，也可能值得迁移。上线后继续看输入长度分布和错误类型，尤其关注逐步增长的长上下文请求。

用同一批真实但已脱敏的样本做 A/B，小流量上线并设置回退阈值。若 Haiku 5.5 的合格率下降，先判断是否能通过提示词、输出约束或分工修复；若需要复杂推理、跨多步代码修改或高风险判断，就应继续让更强模型承担，并让 Haiku 处理外围的窄任务。

## 上线判断：把“便宜”落到每个合格结果

如果你的请求通常短于 10 万 token、任务边界清楚、结果能自动检查，Haiku 5.5 值得进入候选池。如果请求经常超过长上下文档位，或者失败会带来高昂业务损失，则价格优势需要和上下文成本、重试成本及人工复核一起评估。

最稳妥的动作不是一次性替换，而是选一条高频、低风险、可量化的工作流，跑一周影子流量或小比例 A/B，再按“每个通过验收的任务”比较成本与延迟。模型更便宜，只有在任务仍然做对时，才算产品成本真的下降。

如果你现在只先测一类工作流，会优先选分类抽取、客服响应，还是 Agent 子任务？
