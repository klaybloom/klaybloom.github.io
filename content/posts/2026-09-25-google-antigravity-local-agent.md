Google 于 9 月 23 日宣布，Antigravity SDK 支持本地模型工作流，首发组合是 Gemma 4 26B A4B 与 LiteRT。开发者可以让 Agent 在本机运行，断网时继续执行，也可以由云端模型负责规划、本地模型处理具体任务。Google 建议设备拥有超过 24GB 的显存或统一内存。

**这项更新最值得关注的，不是“Agent 从此免费”，而是把一部分代码和请求留在本机成为官方支持的工作方式。** 对独立开发者、处理敏感代码的团队和边缘场景产品来说，现在可以开始评估本地 Agent；但在换硬件或迁移任务前，先确认模型速度、任务质量和工具权限能否接受。

## 这次更新具体改变了什么

Antigravity SDK 是 Google 用于构建智能体应用的开发工具。这次增加了本地推理配置，官方教程展示了如何下载模型、配置 LiteRT，并让 Agent 读取当前目录内容。SDK 还支持连接兼容 OpenAI API 的本地服务，例如 Ollama、LM Studio 或 vLLM，因此已有本地推理环境的团队也可以接入自己的后端。

这意味着开发者可以保留同一套 Agent 编排与工具逻辑，把模型运行位置作为一个可选项。它不等于所有云端模型都能一键替换，也不代表本地模型拥有相同的能力、速度或稳定性。


## 24GB 是建议门槛，不是通用采购结论

Google 推荐超过 24GB 的 VRAM 或统一内存。这个数字来自官方上手说明，具体体验还会受量化方式、上下文长度、并发数和操作系统占用影响。机器满足建议值，只说明值得试跑，并不能保证延迟达到在线产品要求。

先用现有工作站做小规模试点，比立刻采购新设备更稳妥。选一组可重复的真实任务，例如代码解释、测试生成或脱敏文档摘要，记录任务成功率、首 token 延迟、整体耗时、内存占用和人工返工。若还没有合适设备，可先通过本地兼容服务验证接口与权限设计，再决定是否投入硬件。

要特别区分“本地推理”和“整套系统离线”。模型可以在本地运行，但安装模型、下载依赖、访问外部检索、同步文件或调用第三方工具仍可能需要网络。真正的离线部署还要检查这些外围环节，而不能只看模型进程是否在本机。

还要考虑模型文件的体积、启动时间和更新方式。若开发者每次打开项目都要等待模型加载，或者团队设备需要重复下载多个版本，最终使用率可能很低。可先评估模型是否能常驻、更新能否受控，以及设备资源是否会和 IDE、容器、编译任务争抢。对笔记本用户来说，风扇噪声、续航和发热也属于真实成本。

## 混合工作流可能更实用

Google 给出的演示采用“云端规划、本地执行”的分工：云端 Gemini 3.8 Flash 根据文件名和任务描述制定步骤，本地 Gemma 4 26B 处理代码审查、修复候选和测试。官方记录称，在一次演示中 97.2% 的 token 在本地运行，云端使用 95 个 token；这是 Google 展示的单次案例，不是独立基准，也不能直接外推到团队日常负载。

更可落地的做法是按数据敏感度和任务复杂度分层：让本地模型处理可定义、可检查的重复工作；需要更强推理或外部知识时再转给云模型。两边之间传递的信息也应最小化，例如云端只接收任务说明和必要的文件结构，不默认上传源代码、密钥或客户数据。

## 开始试用前，先过三道检查

**第一，测任务，不测模型口碑。** 用团队真实且脱敏的样本，对比本地与现有云端方案的完成率、耗时和返工量。若目标是省成本，计算每个合格结果的总成本，而不是只把 API 账单归零；硬件折旧、等待时间和维护都要计入。

**第二，明确 Agent 的本地权限。** 本地运行减少了数据外传路径，但并不会自动降低工具风险。限制可读写目录，审查 shell、网络和文件操作权限，为会改代码或执行命令的 Agent 保留人工确认与操作日志。

**第三，给混合路由设边界。** 哪类输入可以发往云端、触发条件是什么、失败后如何回退，都应有明确规则。用少量任务灰度，检查网络关闭时的表现、模型加载失败的提示和云端不可用时的降级路径，再决定扩大范围。

## 先把数据边界画出来

本地部署常被理解成“数据不会离开设备”，但实际系统通常不止模型一环。Agent 可能通过浏览器、代码托管平台、包管理器、遥测或日志服务访问外部环境。即使模型本身不上传提示词，插件或工具仍可能把文件内容发出。因此试点时应逐项记录网络请求来自哪个组件、访问了哪些目录，以及错误日志是否包含业务内容。

建议先从脱敏仓库或合成数据开始，关闭不需要的网络工具，再逐个开放所需能力。企业团队还应确认模型权重的来源、许可证、版本固定和漏洞处理流程。若本地和云端路由并存，应在请求级别标记数据分类，让高敏任务只走批准的本地路径；一旦本地模型不可用，不能悄悄把任务回退到云端。

## 谁现在适合试

如果你已经有 24GB 以上显存或统一内存的开发设备，且日常任务包含可验证的代码或文档处理，可以先做离线试点。如果团队受到数据合规要求约束，最先值得验证的是“哪些步骤能不出本机”，而非期待全部业务都能本地化。若硬件不足、任务依赖实时检索或输出错误代价很高，当前更适合先评估混合方案，并保留云端或人工兜底。

Antigravity SDK 这次更新把本地模型从社区拼装方案推进到 Google 官方支持的 Agent 工作流之一。**对开发团队来说，下一步不是先换模型或买设备，而是拿一类真实任务，测出本地运行的质量、延迟和权限边界。**方圆Talk会继续跟踪模型与开发工具变化，并把它们拆解成可验证的产品选择。
