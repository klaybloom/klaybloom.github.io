如果你这两个月认真跑过长上下文 Agent，大概率会有一个感受：模型越来越能干，账单也越来越敏感。

一次代码仓库分析、一次客服知识库问答、一次合同审阅，前面那大段系统提示、工具说明、文档片段和历史对话，很多时候都在重复发送。模型每次都重新读一遍，开发者每次都重新付一遍输入 token。

AIHOT 2026-05-26 日报里有一条很值得产品和技术团队注意：Qwen3.7-Max 隐式缓存功能上线，自动启用，无需额外设置。简单讲，只要你的请求里有可复用的前缀内容，平台会尝试自动缓存命中，命中的输入 token 按更低价格计费。

这不是一个只适合写进更新日志的小功能。对正在做 Agent、代码助手、企业知识库和长文本工作流的团队来说，它会改变产品成本结构。

## 为什么这件事重要

大模型应用的成本，常常不是平均分布的。

短问答产品里，用户每次输入几句话，输出几段话，成本很好估算。但一旦进入 Agent 和企业场景，输入会迅速变重：

| 场景 | 反复出现的输入 |
| --- | --- |
| 代码助手 | 仓库结构、编码规范、工具说明、最近修改 |
| 企业客服 | 系统提示、业务规则、知识库片段、用户历史 |
| 数据分析 Agent | 表结构、字段解释、分析模板、历史步骤 |
| 法务和合同审阅 | 审阅规则、标准条款、风险清单、合同正文 |

这些内容有一个共同点：并不是每轮都完全不同。

以前的做法通常是硬扛。要么把上下文都塞进去，换来更完整的回答；要么人为缩短提示，牺牲效果来控成本。隐式缓存的价值在这里：它让“重复输入”有机会变便宜，而且不要求每个开发者先改一套缓存逻辑。

## 隐式缓存和显式缓存，不是一回事

阿里云 Model Studio 文档把 context cache 分成两类：显式缓存和隐式缓存。

显式缓存需要开发者主动标记缓存边界。它更适合你能明确控制前缀内容的场景，比如固定系统提示、稳定知识库片段、长文档多轮提问。官方文档里提到，显式缓存创建时按标准输入价格的 125% 计费，命中后缓存输入 token 按 10% 计费，有效期为 5 分钟，命中会刷新有效期。

隐式缓存则是自动模式。开发者无需配置，也不能关闭。平台会自动识别公共前缀，命中后缓存输入 token 按标准输入价格的 20% 计费。它的门槛更低，文档中写到最少 256 tokens 就可能进入缓存判断，但命中率不保证，缓存清理也由系统决定。

两者的区别可以这样看：

| 维度 | 隐式缓存 | 显式缓存 |
| --- | --- | --- |
| 是否需要改代码 | 不需要 | 需要设置 `cache_control` |
| 命中确定性 | 不保证 | 可按规则控制 |
| 命中价格 | 标准输入价的 20% | 标准输入价的 10% |
| 最少缓存 token | 256 | 1024 |
| 适合谁 | 先看收益的多数团队 | 对成本和命中率要求高的团队 |

还有一个关键点：一次请求里两种模式不能同时使用。如果你已经用了显式缓存，就不要期待同一次请求再叠加隐式缓存。

## 对开发者来说，先看三个指标

隐式缓存自动打开以后，不代表你可以完全不管成本。真正该做的是把观测补上。

第一，看缓存命中 token。

使用 OpenAI compatible 调用方式时，官方文档提到可以在 `usage.prompt_tokens_details.cached_tokens` 里查看命中的缓存 token 数。这个字段很重要。它能告诉你，到底是缓存真的在省钱，还是你只是以为它在省钱。

```json
{
  "usage": {
    "prompt_tokens_details": {
      "cached_tokens": 8192
    }
  }
}
```

> 对长上下文产品来说，缓存命中不是锦上添花，而是成本表里应该单独观察的一列。

第二，看请求前缀是否稳定。

缓存命中的前提，是请求里存在重复前缀。对 Agent 来说，系统提示、工具说明、固定策略、知识库检索结果的排序，都会影响复用。很多团队的提示词每天变一点，工具列表每轮重排，RAG 片段顺序飘来飘去，都会让缓存效果打折。

第三，看产品路径是否值得优化。

不是所有请求都值得为了缓存改结构。一次性短问答不必折腾。真正值得关注的是**高频、高输入、相似度高**的路径，比如同一份文档连续提问、同一个仓库反复修改、同一套业务规则支撑大量客服对话。

## 产品团队该怎么用这次更新

如果你的产品已经在用 Qwen3.7-Max，先做一件很现实的事：把长上下文请求分组。

不要只看总 token。把请求按业务路径拆成几类：

1. 用户单轮问答。
2. 多轮文档问答。
3. Agent 连续执行任务。
4. 代码仓库分析和修改。
5. 企业知识库客服。

然后观察每类请求的输入 token、缓存命中 token、输出 token、响应时间和单次成本。看一周，基本就能知道隐式缓存对你的业务有没有实际价值。

如果命中已经不错，可以先享受自动收益。如果命中很差，但业务路径明显存在重复前缀，就该考虑整理提示结构，或者在关键路径上使用显式缓存。

## 这件事也提醒我们：模型能力之外，平台能力越来越关键

过去选模型，很多团队只盯三个问题：聪不聪明、快不快、贵不贵。

现在还要加几个问题：

1. 长上下文有没有可观测的缓存收益？
2. 缓存命中字段是否容易接入监控？
3. 显式缓存的边界是否好控制？
4. 不同部署区域和不同模型是否支持同样能力？
5. 价格变化会不会直接改变产品毛利？

Qwen3.7-Max 的隐式缓存上线，表面看是一个平台功能，实际影响的是应用架构。Agent 产品越复杂，重复上下文越多，缓存就越接近核心工程能力。

## 最后

这次更新值得写进团队的模型评估表。

它不一定让所有应用立刻省很多钱，但它给了开发者一个明确方向：不要只优化 prompt 写法，也要优化上下文复用方式。

如果你的 AI 产品正在进入长任务、多轮对话、企业知识库或代码助手场景，今天就可以做一个小实验：找出最贵的 20 条长输入请求，看里面有多少内容其实每次都在重复。

模型越来越强，真正拉开差距的，可能不是谁多塞了几千 token，而是谁先把这些重复 token 管起来。
