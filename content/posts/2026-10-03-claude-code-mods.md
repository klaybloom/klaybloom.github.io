Anthropic 在 10 月 1 日为 Claude Code 推出 mods：开发者可以用 TypeScript 函数改写提示词、拦截或重试工具调用、处理权限请求，还能替换部分内置功能、给终端或桌面界面加控件。mods 随插件分发，可在 Claude Code CLI 和桌面应用中使用。

这不只是多了一种外观主题。过去团队主要通过设置、命令、hooks 和插件扩展编码代理；现在一段 mod 可以介入事件本身，改变模型看到的内容、工具是否执行，以及用户看到的交互。对维护 Claude Code 工作流的开发者和企业管理员来说，定制能力更强了，插件信任也因此变成运行时权限问题。

**先给结论：可以把 mods 当作可编程的工作流扩展层来评估，但不要把它当普通 UI 插件随手安装。** Anthropic 明确说明，mods 与 Claude Code 本身拥有相同的本机访问权限，并没有被沙箱隔离。试用时先用低风险仓库验证，再逐步开放权限。


## 它比普通插件多介入了哪一步

Anthropic 把 mod 描述为挂接 Claude Code 事件流的 TypeScript 函数。事件可以涉及工具调用、权限询问和界面绘制；mod 可以在事件前后运行，也可以包裹事件或直接替代原有处理。结果是它不只“提供一个新命令”，还可以改变代理循环里某些环节的行为。

例如，mod 可以在提示词送进模型前做改写，在工具执行前阻止或修改调用，或者在工具输出进入上下文前遮掉秘密信息。它也能处理权限请求，或新增按钮、输入框和信息面板。多个 mods 若挂在同一事件上，会依加载顺序依次运行，因此排查行为时还要知道有哪些扩展先后参与。

这让 hooks、插件和 mods 的边界更值得团队重新梳理：重点不在名称，而在代码能否影响代理输入、工具调用和权限决策。Anthropic 称部分内置功能已经以 mod 方式提供，比如 `/diff`，用户可以停用或换成自己的版本；官方也计划逐步迁移更多内置功能。

## 三种值得先试的场景

第一种是把团队规则做成可见的工作流提示。比如在会话面板展示 CI 状态，或在执行高风险命令前明确呈现环境和影响范围。这类扩展能减少开发者在终端、工单和流水线之间来回确认的成本，但状态来源必须可靠；面板显示“通过”不应取代 CI 本身的结果。

第二种是把生产操作的人工确认嵌进流程。Anthropic 举例说明，团队可以用 mod 在触及生产配置的命令前要求确认。关键在于确认策略应由组织管理、可审计且无法被低信任扩展绕开。把提醒按钮写进一个随意安装的个人插件，不等于建立了生产保护措施。

第三种是增加审计和上下文清理。例如，较早加载的 mod 可以记录其他 mods 的调用；另一个 mod 可以在模型读取工具结果前遮盖秘密。它们适合帮助团队看见扩展链条，但同一权限模型也意味着记录文件本身可能含敏感信息，必须设定保留期限、访问权限和脱敏规则。

## 安全边界要先于功能清单

Anthropic 对权限模型的提醒很直接：mod 未被沙箱隔离，拥有 Claude Code 同等的机器访问能力。因此，阅读 TypeScript 源码、检查依赖、确认发布者和审视更新渠道，不是可选的“高级用户习惯”，而是安装前的基本动作。尤其当 mod 能拦截工具或处理权限请求时，团队要确认它究竟能改写什么、失败时如何处理，以及行为能否被用户察觉。

Team 与 Enterprise 计划，以及使用托管设置的机器上，Anthropic 提供先加载的内置 `sec-default` mod，用于阻止用户安装的 mods 做某些高风险操作，例如覆盖权限拒绝规则。管理员也可以让自有 mods 先加载，但官方提醒应把 `sec-default` 一并纳入配置，以保留它的限制。组织可通过管理控制台或托管设置控制插件市场。

这类保护仍不能简化成“启用了安全 mod，所以安装都安全”。管理者仍需验证实际加载顺序、组织策略是否生效、用户能否从其他来源绕过，以及更新后策略有没有回归。个人开发者也应把 mod 来源和权限当成可执行代码来审查，而不是只看商店描述和演示视频。


## 团队试用前先做这三件事

**一，建立允许安装的来源清单。** 先限定插件市场或内部仓库，要求每个 mod 有明确维护者、源码和版本记录。对带有提示词改写、工具拦截、权限审批或输出脱敏能力的扩展，标出它挂接的事件、访问的数据和预期失效方式。

**二，在低风险项目验证冲突和加载顺序。** 使用不含生产凭据的测试仓库，观察 mod 如何与现有 hooks、权限规则和其他 mods 协作。尝试让 mod 拒绝调用、修改输入、报错和被停用，确认 Claude Code 与用户分别会看到什么。测试记录里写清版本和配置，避免只留下“能用”的印象。

**三，把生产控制放进组织管理，而不是单人习惯。** 若要拦截生产命令或记录审计信息，先确认托管设置、管理策略和日志保留方案。明确谁能批准安装、谁能更新、谁负责回滚。对于具有高影响的权限请求，保留独立的人工审批路径，不要只依赖 mod 自己对自己做保证。

## 判断

Claude Code mods 让工作流定制从“在旁边加工具”推进到“可以参与代理事件的处理”。这给团队做安全护栏、状态面板和自有交互提供了新入口，也扩大了插件代码的影响范围。最适合的做法不是抢先装满扩展，而是挑一个低风险且可衡量的场景，经过权限、兼容和回滚检查后再推广。

**如果只能先试一种团队 mod，你会优先做生产命令确认、CI 状态面板，还是工具输出脱敏？**
