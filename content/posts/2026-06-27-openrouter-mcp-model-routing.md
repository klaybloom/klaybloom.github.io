过去一年，很多 AI 产品团队都有同一种焦虑：

模型越来越多，名字越来越像，价格表越来越长，基准榜单越来越分散。今天刚把 Claude、Gemini、DeepSeek、Qwen、GLM、Llama 的方案比较完，明天又冒出一个更便宜、更快、在某个任务上更强的新选择。

真正麻烦的地方不在于“没有模型可选”，而在于选择本身已经变成了日常工作。

AIHOT 6 月 26 日日报里，OpenRouter 发布 MCP 服务器这条消息值得单独拿出来看。它不像一个普通工具更新，更像是把“模型情报”接进开发现场：编程智能体可以直接查询实时模型数据、基准排名、定价、端点和文档，还能发起测试推理。

换句话说，模型选择不再只发生在浏览器标签页、Notion 表格和微信群讨论里，它开始进入 IDE、Agent 和自动化工作流。

![从浏览器查表到 Agent 内选型](/images/posts/2026-06-27-openrouter-mcp-model-routing/image-01.webp)

## 以前选模型，像在维护一张永远过期的表

做 AI 应用的人都熟悉这个流程：

先打开几家模型平台，看价格；再翻 benchmark，看编码、推理、长文本、视觉能力；再搜社区反馈，看有没有稳定性、限流、上下文、工具调用方面的问题；最后在代码里改 model name，跑几组样例。

这个流程有三个问题。

第一，信息不在一个地方。价格在平台，基准在第三方榜单，实际体验在社区讨论，端点和参数又在文档里。

第二，信息变化太快。今天性价比最好的模型，可能下周就被新版本或降价打掉。

第三，选型和开发是分离的。开发者真正需要做判断时，往往正在写代码、调 Agent、看失败日志，而不是坐下来做一份采购报告。

OpenRouter MCP Server 的价值就在这里：它不是再做一个网页排行榜，而是让编码智能体能在工作上下文里查这些信息。

根据 AIHOT 摘要，这个 MCP Server 提供的工具包括 `models-list`、`model-get`、`model-endpoints`、`benchmarks`，也支持通过 `chat-send` 发送测试提示，比较不同模型的输出。它整合了 Artificial Analysis、Design Arena 和 OpenRouter 自身排名数据，还能覆盖定价和文档。

这对开发者意味着一件事：以后问“这个任务用哪个模型更合适”，可以少一点凭印象，多一点现场证据。

## 这不是“又多一个 MCP”，而是模型供应链进入 Agent

MCP 过去几个月已经很热，但很多 MCP Server 本质上是在给 Agent 接外部工具：读文件、查数据库、调浏览器、访问 GitHub、连内部系统。

OpenRouter 这次有点不一样。它接入的不是业务工具，而是模型市场本身。

这会改变三个角色的工作方式。

对开发者来说，模型选型会更接近测试驱动。你可以让 Agent 查询当前可用模型，按价格、上下文长度、编码能力、延迟和端点情况列出候选，再用同一段提示词做快速试跑。

对产品经理来说，模型能力和成本不再只是技术团队口头汇报。一个功能要不要上多模型路由、免费版用什么模型、付费版升级到哪档模型，都可以基于更透明的数据讨论。

对创业团队来说，这会降低试错成本。小团队最怕的是把时间花在错误的模型组合上：贵、慢、不稳定，或者一开始很好，规模上来后成本压不住。模型情报进入 Agent 后，选型可以变成持续动作，而不是项目开始时的一次决定。

## 真正值得关注的是“动态路由”会变得更普通

今天很多 AI 产品仍然把模型写死：

- 聊天用一个模型
- 代码用一个模型
- 摘要用一个模型
- 便宜任务用一个小模型

这种做法简单，但越来越不经济。

因为不同模型的优势正在变得更细。一个模型可能在代码修复上强，另一个模型可能在长文摘要上便宜，另一个模型可能在结构化输出上更稳定。再加上价格、延迟、上下文、可用地区和限流策略，单一模型很难一直是最优解。

OpenRouter MCP Server 把实时信息接给 Agent 后，一个自然方向就是：让 Agent 在任务开始前先判断模型，而不是让人提前写死配置。

比如：

| 任务 | 过去的做法 | 新的可能 |
|---|---|---|
| 修复一个复杂 bug | 固定使用某个编码模型 | 查询当前编码榜单、价格和上下文，再试跑候选 |
| 批量改写营销文案 | 使用默认通用模型 | 按成本和质量选择便宜但稳定的模型 |
| 分析长文档 | 手动找长上下文模型 | 直接筛选上下文长度、价格和可用端点 |
| 做多模型评测 | 人工复制提示词 | Agent 调用 `chat-send` 做对比 |

这不代表人不需要判断。相反，人要把判断标准说清楚：质量优先、成本优先、延迟优先，还是合规和稳定性优先。

Agent 负责查数据、跑样例、给候选；人负责定策略。

## 对中文团队的实际建议

如果你在做 AI 产品，OpenRouter MCP Server 这类工具可以从三个地方开始用。

第一，把模型选型从文档搬进开发流程。

不要只维护一张“当前推荐模型”的表。更好的方式是让开发者在写功能、调提示词、做评测时，能直接查询候选模型和价格。表格可以保留，但它应该是决策记录，不应该是唯一信息来源。

第二，为不同任务建立评测提示词。

模型情报再实时，也不能替你定义产品质量。客服、代码、搜索、摘要、表格抽取、内容生成，每类任务都应该有自己的样例和评分标准。没有样例，所谓“模型更强”就会变成泛泛而谈。

第三，把成本看成产品指标。

AI 应用的毛利不是上线后才发现的。Token 价格、调用次数、失败重试、长上下文浪费、多模型路由策略，都会进入最终成本。越早把价格查询和试跑比较纳入工作流，越不容易在增长后被账单教育。

这条新闻最值得看的地方，不是 OpenRouter 又发布了一个 MCP Server，而是它提示了一个方向：

模型市场变化太快，单靠人肉查表已经跟不上了。

以后成熟的 AI 团队，很可能会把模型选择、价格比较、基准查询、样例试跑都放进 Agent 工作流。模型不再是写在配置文件里长期不动的常量，而会变成一个持续被观察、比较和替换的供应链。

对开发者和产品人来说，这不是多学一个工具的问题。

这是 AI 应用开发正在进入下一阶段：从“会调用模型”，走向“会管理模型组合”。
