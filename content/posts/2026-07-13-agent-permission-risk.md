今天看 AIHOT 日报，最让我停下来的不是新模型评测，也不是某个工具版本更新。

是一条很刺眼的事故：一位 AI 创业者把本地 Agent 开了 Full Access，让 subagent 执行文件清理任务，结果 shell 变量里的 `$HOME` 路径解析出错，Agent 执行了危险删除命令，把整台 Mac 上多年的代码、文件和照片清掉了。

这件事不适合只当成“某个模型犯错”的八卦。

它真正提醒我们的是：Agent 已经从聊天框走进终端、文件系统、浏览器和真实业务数据。以前模型说错一句话，最多是内容质量问题；现在 Agent 执行错一步，可能就是文件丢失、订单误改、客户数据外泄。

模型越强，权限越不能粗放。

## 事故的关键，不是模型名

这类新闻很容易被写成模型阵营对比：哪家模型更可靠，哪家模型更危险。

但对开发者来说，更该关注的是执行链路。

从 AIHOT 日报描述看，事故里有几个危险因素叠在一起：

- 本地 Agent 拥有 Full Access；
- 任务涉及文件清理，本身就是高风险操作；
- subagent 参与执行，调用链更长；
- shell 变量路径解析错误；
- 删除命令没有人工确认；
- 没有先做 dry run 或快照；
- 任务过去安全运行过很多次，让人降低警惕。

最后一点尤其重要。

很多团队会把“以前没出事”当成安全依据。但 Agent 系统的问题恰好在这里：同一个任务，只要上下文、路径、变量、模型输出或工具状态发生一点变化，执行结果就可能完全不同。

脚本通常是确定性的。Agent 不是。

![事故链路示意](/images/posts/2026-07-13-agent-permission-risk/image-01.webp)

## Full Access 不该是产品默认值

对很多 AI 工具来说，Full Access 很诱人。

它演示效果好：不用频繁询问，能直接读文件、改代码、跑命令、开浏览器、整理目录。用户看到的是“它真的会干活”。

但产品一旦进入真实工作流，默认权限就会变成风险源。

合理的权限设计，应该把操作分层：

| 操作类型 | 合理默认行为 |
| --- | --- |
| 读取文件、搜索文本 | 可以自动执行，并展示范围 |
| 新建普通文件 | 可以执行，但要说明位置 |
| 修改已有文件 | 先展示 diff，再确认 |
| 移动、覆盖、批量重命名 | 先列清单，再执行 |
| 删除文件、清空目录、改系统配置 | 默认禁止，必须二次确认 |
| 执行含通配符或变量的危险命令 | 先展开实际目标，再让用户确认 |

这里的重点不是多弹几个确认框。

真正有价值的是让用户看见 Agent 准备操作什么：路径是什么，文件有多少，是否跨出项目目录，是否涉及用户目录，是否包含不可逆动作。

如果产品只给一个“允许访问全部文件”的按钮，本质上是在把工程风险转嫁给用户。

## 开发者要给 Agent 加三道门

本地 Agent 要进入日常开发，不能只靠模型自觉。

第一道门，是作用范围。

Agent 应该明确知道当前工作区在哪里。默认只能读写项目目录，除非用户单独授权。只要命令目标跨出工作区，比如指向 `/Users/xxx`、`$HOME`、`/`、外接硬盘或云盘目录，就应该暂停。

第二道门，是执行预览。

文件清理、批量移动、替换、格式化、数据库迁移，都应该先生成操作清单。用户看到“将删除 37 个文件，其中 2 个在项目外”，和只看到“我来清理一下”，完全不是一回事。

第三道门，是恢复能力。

高风险操作前至少要有一种恢复手段：Git 状态检查、备份目录、系统废纸篓、数据库事务、对象存储版本、云端快照。没有恢复能力的自动化，不应该直接碰生产数据。

这三道门不复杂，但很少有产品认真做好。

## 创业团队该把安全做成体验

很多 AI 创业团队会担心：权限确认太多，会不会影响用户体验？

会。

但这不是“安全”和“体验”的二选一。更好的做法，是把安全设计成可理解的工作流。

比如，一个本地代码 Agent 可以这样处理危险命令：

1. 识别命令风险级别；
2. 展开变量和通配符；
3. 显示将影响的路径和文件数量；
4. 如果目标在项目外，直接标红；
5. 默认给出更安全的替代动作；
6. 执行后记录操作日志。

这不是拖慢效率，而是让用户敢把真实任务交给它。

AI 产品的信任不是靠文案建立的。用户要看到：它知道自己在做什么，也允许我在关键时刻拦住它。

## “更聪明的模型”解决不了所有问题

AIHOT 同一天还有另一条新闻：OpenAI 发布 GPT-5.6 系列医疗评估结果，声称在多个医疗任务上显著优于医生；还有 Claude Code 版本更新，修复了终端冻结、远程托管设置同意状态等问题。

这些新闻放在一起看，信号很清楚。

一边是模型能力继续上升，进入医疗、编程、具身智能等更复杂场景；另一边是工具链仍然会在终端、权限、路径、交互状态这些细节上出问题。

能力突破值得兴奋，但真实产品的可靠性往往死在细节里。

一个 Agent 可以写 100 万行代码，也可能因为一个路径变量误删用户目录。一个模型可以通过复杂评测，也可能在真实环境里误解一个按钮、一个文件名、一段 shell。

所以开发者不能只问“模型够不够强”。

还要问：

- 它能不能解释即将执行的动作？
- 它能不能在危险操作前停下来？
- 它能不能把实际路径展示给用户？
- 它能不能在失败后保留证据？
- 它能不能把高风险动作交还给人？

这些问题，才决定 Agent 能不能进入生产环境。

## 真正的产品机会

这次事故给创业者的启发，不是“别做 Agent”，而是 Agent 产品还有大量基础设施机会。

比如：

| 方向 | 可以做什么 |
| --- | --- |
| 权限沙箱 | 限定 Agent 的文件、网络、命令访问范围 |
| 操作审计 | 记录每次工具调用、参数、结果和影响文件 |
| 风险识别 | 自动标记删除、覆盖、批量修改、外部目录访问 |
| 执行预览 | 把命令结果转成用户能看懂的清单 |
| 恢复系统 | 自动备份、版本管理、快照和回滚入口 |
| 团队策略 | 为不同角色配置可执行动作和审批规则 |

这些东西看起来没有大模型发布耀眼，但它们会决定企业是否敢用。

未来的 Agent 平台，竞争点不会只是模型排行榜。谁能让 Agent 在真实环境里少犯不可逆错误，谁就更接近长期价值。

## 今天的提醒

如果你正在做本地 Agent、代码助手、浏览器自动化、数据分析助手或办公自动化工具，建议今天就检查三件事：

第一，危险命令有没有识别和确认。

第二，项目外路径有没有默认拦截。

第三，高风险操作前有没有可恢复方案。

不要等事故发生后再补。

Agent 时代，用户授权的不只是“让 AI 帮我干活”。

用户真正交出去的，是一部分执行权。

而执行权，必须被设计得比聊天框更严肃。
