昨天看 AIHOT 日报时，有一条不算最热闹，但很值得产品和开发团队认真看：

GitHub 开源了 Spec Kit，一个用产品规格引导 AI 编码的工具包。

它要解决的问题很具体：现在很多人用 AI 写代码，习惯先扔一句需求，然后等 agent 自己理解、自己设计、自己实现。速度看起来很快，但真正进入业务项目后，麻烦通常出现在同几个地方：边界没讲清楚、异常场景没人定义、技术方案和产品目标对不上、最后还要人反复改。

Spec Kit 的思路正好相反。

不是让 AI 一上来写代码，而是先把产品规格写清楚，再让 AI 围绕规格去澄清、规划、分任务、实现。

这件事对中文 AI 创业者、开发者、产品人都有价值。因为它提醒我们：AI 编码的下一个竞争点，可能不是谁的提示词更花，而是谁能把需求写成 agent 可以执行的规格。

## 从“提示 AI 写代码”到“让规格驱动实现”

Spec Kit 的关键词是 Specification-Driven Development。

可以把它理解成一套面向 AI agent 的开发流程：

1. 先写清楚产品想实现什么；
2. 再让 AI 找出不明确的地方；
3. 然后形成技术计划；
4. 再拆成任务；
5. 最后交给 agent 执行。

![规格驱动流程图](/images/posts/2026-06-07-spec-kit-ai-coding/image-01.png)

这和传统 PRD 不完全一样。

传统 PRD 更多是给人看的，语言可以有弹性，也可以留一点上下文给团队成员自己补全。Spec Kit 里的规格更接近“开发合约”：它要让 Copilot、Claude Code、Codex、Gemini、Cursor、Qwen 这类工具都能读懂，并且能据此执行。

换句话说，规格不再只是沟通材料，而是开发流水线的一部分。

## 为什么这件事现在重要

过去一年，很多团队都经历了同一个过程：

先是觉得 AI 编码很神奇。一个页面、一个脚本、一个后端接口，几分钟就能生成。

再往后做真实项目，就会发现问题不在“AI 会不会写代码”，而在“它到底有没有理解你要什么”。

如果需求只停留在一句“帮我做一个会员系统”，agent 很容易立刻开始生成数据库表、页面、接口和状态逻辑。但它不知道会员等级怎么定义，不知道退款和过期怎么处理，也不知道哪些字段涉及合规和审计。

人类开发者遇到不明确的需求，通常会停下来问。AI agent 更常见的行为是先给一个看似完整的实现。

这就是 Spec Kit 要改变的地方。

它把“开始写代码”往后推了一步，把“先澄清规格”放到前面。对于团队来说，这不是降低效率，而是减少后面返工。

## 产品经理也要适应这种工作方式

Spec Kit 对开发者有用，但它真正影响的不是开发者一个角色。

产品经理也要重新思考需求文档的写法。

以前写需求，重点是让人理解业务意图。以后写给 AI agent 的规格，还要让它能判断：

| 规格项 | 需要写清楚的问题 |
| --- | --- |
| 用户目标 | 用户为什么要用这个功能 |
| 功能边界 | 哪些场景不属于本期 |
| 数据规则 | 字段、状态、权限如何变化 |
| 异常处理 | 失败、重复、撤销、超时怎么处理 |
| 验收标准 | 什么结果算完成 |

这些内容过去也重要，只是很多团队靠口头沟通消化掉了。AI agent 进入流程后，隐含信息会变得更贵。

你没写，它就会自己补。

## 开发者的价值不会消失，但位置会变化

Spec Kit 也给开发者一个现实提醒：未来写代码本身会继续变快，但判断规格、识别风险、设计边界会更重要。

开发者不只是等 agent 生成代码，再做人工审查。更有效的做法是提前参与规格阶段，把技术约束写进计划里。

比如一个看似简单的“导出报告”功能，至少要先明确：

- 数据量上限是多少；
- 导出任务是否异步；
- 用户是否能重复提交；
- 文件保存多久；
- 权限变化后旧链接是否仍可访问；
- 失败后是否能重试。

这些问题不写进规格，AI 也许能生成一个按钮和一个下载接口，但很难生成一个真正可上线的功能。

## 小团队可以怎么用

如果你现在已经在用 Codex、Claude Code、Cursor 或 Copilot，没必要等团队引入完整流程才开始。

可以先做一个很轻的版本：

1. 每个功能先写一页规格，包含目标、边界、数据规则和验收标准；
2. 让 agent 先指出规格里不清楚的地方，不允许它直接写代码；
3. 澄清后再让 agent 输出技术计划；
4. 计划确认后，再拆任务实现；
5. 每个任务都附带验收条件。

这套流程的重点不是“文档更多”，而是把人脑里的隐含判断，提前变成 agent 能理解的输入。

## 这可能是 AI 编程进入团队协作的信号

AI 编码早期像个人效率工具：谁会提示，谁就更快。

但它进入公司项目后，就必须面对协作、边界、质量和责任。Spec Kit 这类工具的出现，说明行业正在从“让 AI 快点写”走向“让 AI 按清楚的规则写”。

对开发者来说，值得关注的不只是某个工具本身，而是背后的方向：

产品规格会变得更结构化，技术计划会更早生成，任务会更适合交给 agent 执行，代码审查也会回到规格和验收标准上。

这可能不是最热闹的 AI 新闻，但很实用。

因为真正能把 AI 用进团队的人，靠的不是一句神奇提示词，而是把需求、计划和执行连接起来的工作方式。
