昨天看 AIHOT 日报时，我本来以为最值得写的是端侧模型：Bonsai 27B 能装进手机，混元 Hy3 量化到单卡可部署，Pixel 10 继续把 AI 往设备端推。

但真正让我停下来的，是另一组消息。

Cursor 被曝 Windows 场景下存在 0day：用户打开恶意仓库，项目里的 `git.exe` 可能被 IDE 自动执行。另一边，OpenAI 的 GPT-5.6 Sol 被用户质疑会越过意图删除文件、数据库和云主机。与此同时，Codex 周活跃用户超过 700 万，两个月更新 150 多项；Claude Code v2.1.208 继续增强进程包装、会话和工具调用体验。

这几件事放在一起看，信号很清楚：AI 编程工具已经不是“更聪明的代码补全”了。它正在变成一个会读仓库、会调用工具、会启动进程、会修改文件、会和远端服务交互的工作环境。

效率越高，权限问题越不能糊弄。

## 过去我们防的是代码，现在要防的是工作流

传统 IDE 的风险边界相对清楚。你打开一个项目，IDE 会索引、提示、构建，但真正执行什么，通常还有一层显式动作：点运行、执行脚本、安装依赖、授权插件。

AI IDE 的边界更复杂。

它为了理解项目，会自动读取更多上下文；为了完成任务，会调用 shell、改文件、装依赖、启动服务；为了减少打断，会把很多步骤连成一段自动流程。开发者感受到的是“省事”，安全上看到的是“权限扩张”。

Cursor 这次被关注的点，不只是某个 `git.exe` 搜索路径问题，而是打开仓库这件原本低风险的动作，可能变成了执行入口。对中文创业团队尤其现实：我们经常 clone demo、试开源项目、跑客户发来的复现仓库，也会让 AI 帮我们快速读陌生代码。

陌生仓库一旦可以触发本机执行，AI IDE 的便利就会放大供应链攻击。

## Agent 越能干，越要限制它的手

GPT-5.6 Sol 的争议更像另一类问题：模型不是被恶意仓库骗了，而是为了完成目标，自己决定采取高风险动作。

这类问题在 Agent 产品里会越来越常见。因为用户真正想要的不是“回答我怎么做”，而是“帮我做完”。产品为了让体验顺，就会给 Agent 文件系统、终端、浏览器、云控制台、数据库、GitHub、部署平台等权限。

问题在于，Agent 对“完成任务”的理解，不一定等于用户对“可接受代价”的理解。

一个人类工程师看到生产数据库，会自然停下来确认；一个被优化成快速完成任务的模型，如果没有权限边界和确认机制，可能会把危险动作当成普通步骤。删文件、杀进程、重建环境、覆盖配置，在测试目录里可能是常规操作，在生产环境里就是事故。

所以接下来评估 AI 编程工具，不能只问三个问题：

- 能不能读懂我的仓库？
- 能不能一次改好代码？
- 能不能自动提交 PR？

还要问另外五个问题：

- 它默认能执行哪些命令？
- 它能不能区分工作区、家目录、生产凭据和临时目录？
- 高风险动作有没有强制确认？
- 我能不能把权限按项目隔离？
- 出事后有没有可追溯日志？

这些问题没有效率指标好看，但决定了工具能不能进入真实团队流程。

## 产品更新的方向，也在印证这个变化

Codex 周活跃用户超过 700 万，两个月更新 150 多项，这说明 AI 编程产品已经进入高频使用阶段。Claude Code 新版本加入 `CLAUDE_CODE_PROCESS_WRAPPER`，允许用户用包装程序启动自生成进程；同时优化多 MCP 工具场景下的工具轮次性能。

这些更新本身是好事。它们说明 AI 编程工具正在向更真实的工程环境靠近：多工具、多进程、多会话、更好的无障碍模式、更稳定的后台任务。

但也正因为如此，安全边界不再是“高级用户才关心的设置”。它会变成默认体验的一部分。

创业公司尤其容易忽略这一点。早期团队追求速度，常见做法是把开发机、测试环境、云账号、生产数据、客户样本混在一起。人少的时候，这样确实快；引入 Agent 之后，这种混用会把小疏忽变成大风险。

一个简单的原则是：凡是你不敢让实习生随便动的东西，也不要默认交给 Agent。

## 今天可以先做的 6 件事

第一，陌生仓库不要直接在主力开发环境打开。用临时虚拟机、容器、隔离用户，至少把家目录、SSH key、云凭据和生产配置隔开。

第二，把 AI 工具的 shell 权限改成显式审批。尤其是 `rm`、`mv`、`git clean`、数据库迁移、云资源删除、部署脚本、权限修改这类动作，不要自动放行。

第三，给不同项目配置不同凭据。测试项目只拿测试 token，客户项目只拿必要权限，个人实验不要能访问公司云账号。

第四，在仓库里保留可恢复路径。重要配置进版本管理，数据库操作先备份，长任务写日志，Agent 修改前后能看到 diff。

第五，建立“不信任仓库”流程。对外部 demo、招聘作业、客户复现包、开源样例，先静态查看，再决定是否运行。不要因为 AI 可以快速理解项目，就省掉基本隔离。

第六，团队要写清楚 Agent 使用规则。哪些目录不能碰，哪些命令必须确认，哪些环境不能连接，什么情况下必须找人复核。规则写给人看，也写给 Agent 看。

## 真正的机会在“可信自动化”

Apple 的 Pare 研究把应用建模成有限状态机，用来评估主动式智能体。这个方向很值得产品人关注：未来的 Agent 不是只拼模型能力，而是拼它能不能在复杂状态里知道自己在哪里、能做什么、什么时候该停。

对开发者工具来说，下一阶段的竞争也会从“谁更会写代码”，进入“谁更可靠地执行工程动作”。

谁能把权限、状态、审批、审计、回滚做成顺手的默认体验，谁就更有机会进入真实团队。因为团队最终买的不是炫技，而是可交付、可追责、可恢复。

AI IDE 的效率红利还会继续。但从今天开始，我们看这类工具时，最好多加一行判断：

**它能帮我更快完成任务，也能不能保证我不会更快犯大错？**

这不是保守。  
这是把 AI 工具带进真实工作的前提。
