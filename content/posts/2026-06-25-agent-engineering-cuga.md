过去一年，很多团队做 Agent 产品时，都有一个相似的起点：先选模型，再写 Prompt，再接几个工具。

演示时很顺。让它查资料、改表格、写邮件、整理报告，好像都能动起来。

但一进真实业务，问题就变了：工具调用失败怎么办？中间状态丢了怎么办？多轮任务执行到第十步，前面查到的结果还能不能被正确引用？哪些操作必须人工确认？客户要求私有化部署时，原来的 Agent 能不能搬过去？

AIHOT 2026-06-24 日报里，IBM 开源的 CUGA 值得拿出来单独看，不是因为它又发明了一个新名词，而是因为它把 Agent 真正难的部分摆到了台面上。

它提醒我们：**Agent 产品的核心，正在从“模型会不会回答”转向“系统能不能可靠执行”。**

## CUGA 到底是什么

CUGA 全称是 Configurable Generalist Agent，IBM 把它定位成面向企业的开源 Agent harness。

这个词不好直译。你可以把它理解成 Agent 的执行骨架：它不只是让模型调用工具，而是把规划、执行、状态管理、反思、策略约束和部署方式都放进同一套运行时里。

Hugging Face 上的 IBM Research 文章把它讲得很直接：开发者不需要从零开始写工具编排、执行循环和状态同步，而是提供工具列表和系统提示词，然后由 CUGA 负责下面那层运行机制。

这和很多“写一个 Agent demo”的差别很大。

Demo 关心的是：模型能不能调到这个工具。

CUGA 关心的是：这个工具调错了、失败了、要人工批准、要被审计、要换模型、要换部署环境时，系统还能不能继续工作。

## 真正省下来的，不是几行代码

如果只看示例代码，CUGA 的使用方式并不夸张：创建一个 `CugaAgent`，传入模型、工具、指令和状态目录。

这看起来只是少写了一些样板代码。

但对真实团队来说，省下来的不是几行代码，而是一整套反复重做的工程判断：

- 工具接口应该怎么写，才能让 Agent 知道成功和失败；
- 长任务中间产生的变量和结果应该放在哪里；
- 出错后是继续、重试、换路径，还是停止；
- 哪些工具可以直接执行，哪些必须等人批准；
- 同一个 Agent 能不能从本地开发搬到隔离环境；
- 模型从 OpenAI 换成 watsonx、Ollama 或本地模型时，业务代码要不要改。

这些问题在产品早期经常被忽略。因为早期只要一个 demo 能跑，团队就会觉得方向已经通了。

但只要 Agent 开始接触客户数据、业务系统、内部知识库和生产工具，这些问题就会一起出现。

## 为什么“单文件示例”有价值

这次 CUGA 相关发布里，我更在意的是那二十多个单文件示例应用。

它们不是为了证明 IBM 会写 demo，而是把一个重要信号放出来：Agent 应用需要可复制的骨架。

今天很多团队做 Agent，很容易陷入两种状态。

一种是“Prompt 工程化”。所有规则都堆在系统提示词里，工具越接越多，最后没人知道某条规则为什么存在。

另一种是“框架依赖化”。用了一个很重的框架，初期上手快，但一到权限、审计、部署、私有数据边界，团队又要在框架外面再包一层。

CUGA 的示例思路更朴素：每个应用都围绕工具和指令展开，通用能力交给 MCP、OpenAPI、LangChain 函数这类接口，特定业务逻辑留在自己的代码里。

这对创业团队很实用。

如果你要做一个销售线索 Agent，不必先设计一整套平台；你可以先明确它能访问哪些数据源、每一步应该产出什么结构、哪些操作需要审批。

如果你要做一个企业知识库 Agent，也不必一开始就把所有文档都塞进 Prompt；你应该先定义它如何检索、如何引用、如何处理找不到答案的情况。

## Agent 的难点在边界

CUGA 最值得产品人看的地方，是它把“边界”当成一等公民。

Agent 不是普通聊天机器人。它会调用外部工具，会读取数据，会写入系统，会在多步任务里做决定。

一旦它能行动，问题就不再是“回答得像不像人”，而是：

- 它有没有权限做这件事；
- 它有没有先查到必要证据；
- 它的每一步有没有日志；
- 它失败时有没有可解释的原因；
- 它会不会越过业务规则；
- 它能不能被撤销、被限制、被复盘。

这些问题不解决，Agent 产品很难从内部试用走向客户交付。

所以 CUGA 里的 policy、tool approval、playbook、output formatter 这些设计，虽然没有模型发布那么吸引眼球，却更接近企业真正愿意买单的部分。

## 对中文团队的启发

今天做 Agent 的中文团队，容易被两个方向带偏。

一个方向是过度追新模型。模型当然重要，但如果产品的工具层、权限层和状态层很薄，再强的模型也会把问题放大。

另一个方向是过早做大平台。还没有跑通几个稳定场景，就先做低代码编排、可视化画布、插件市场，最后平台很完整，真正可交付的 Agent 不多。

CUGA 给出的启发更实际：

先把一个 Agent 的执行链条做清楚。

它能用什么工具，不能用什么工具；它每一步产出什么结构；失败怎么表达；哪些动作需要人同意；运行记录怎么保存；模型和部署环境怎么替换。

这些事情做好，一个 Agent 才有机会从“能演示”变成“能交付”。

## 今天应该记住什么

AIHOT 2026-06-24 的日报里，有很多更容易上标题的消息：视频模型更快了，音频模型更强了，大厂又发了新能力。

但对正在做 AI 产品的人来说，CUGA 这条更值得停一下。

因为 Agent 的竞争，很快不会只是谁能接入最强模型。

真正拉开差距的，会是团队能不能把工具、状态、策略、沙箱、日志、评估和部署这些基础能力做成稳定系统。

模型决定上限，工程决定能不能交付。

如果你的产品路线里已经写了“Agent”，现在就该问一个更具体的问题：

这个 Agent 离开演示环境以后，还能不能可靠地完成任务？
