昨天看 AIHOT 日报时，有一条消息不算最热闹，却很值得开发者停下来：OpenAI API 新增了内容审核评分，Responses API 和 Chat Completions API 都能在生成请求里返回 moderation scores。

这件事表面上是多了一个参数。真正的变化是，AI 产品的安全链路不用再总是“先生成、再另发一次审核请求、再决定能不能展示”。它可以变成一次请求里的两个信号：输入有没有风险，输出有没有风险。

对创业团队来说，这类变化比模型榜单更实际。因为你迟早会遇到这些问题：用户输入边界模糊，模型拒答也可能含有敏感描述，客服和社区场景需要留痕，人工审核队列不能全靠关键词，产品又不能因为每条消息多一次网络请求就变慢。

## 它到底新增了什么

OpenAI 官方文档里给出的用法很直接：在生成请求里加一个顶层 `moderation` 对象，指定 `omni-moderation-latest`。API 会在同一次生成结果里返回输入和输出的审核结果。

```js
const response = await client.responses.create({
  model: "<your_generation_model>",
  input: [
    {
      role: "user",
      content: "用户输入内容",
    },
  ],
  moderation: { model: "omni-moderation-latest" },
});

const inputModeration = response.moderation.input;
const outputModeration = response.moderation.output;
```

这里有两个要点。

第一，它不是替代原来的 `/v1/moderations`。如果你的应用只想审核一段文字或一张图片，不需要生成回答，独立审核接口仍然适合。

第二，它也不是“返回 true 就拦截，返回 false 就放行”的万能开关。官方文档明确提醒，`flagged` 适合做第一层判断，`categories` 和 `category_scores` 更适合日志、分流、审计和人工复核。

换句话说，**分数不是产品政策本身。分数只是让你更容易执行自己的政策。**

> 对产品团队来说，审核结果的价值不在于替你做最终决定，而在于把风险信号提前放到可记录、可复查、可调整的位置。

## 产品团队该怎么用

最直接的场景是聊天产品。

过去很多团队会做两段式流程：用户发消息后，先调用模型生成；生成完再调用审核接口；审核过了才展示。这个流程能做，但每多一次请求，就多一次延迟和失败点。

现在可以把流程改成这样：

1. 请求生成时同步拿到输入审核结果和输出审核结果。
2. 输入高风险时，不一定取消生成，但可以进入更严格的回答模板。
3. 输出高风险时，先不展示给用户，转为安全提示或人工复核。
4. 低风险但分数接近阈值时，记录日志，用来调整产品策略。

这对客服、教育、医疗科普、社区问答、创作工具都很有用。因为这些产品通常不是“有风险就关闭功能”，而是要区分不同程度：直接拦截、降低模型自由度、换回答模板、提醒用户、进入人工复核。

表格里可以这样看：

| 场景 | 更合适的处理 |
|---|---|
| 输入被标记 | 降低回答自由度，避免模型继续放大风险 |
| 输出被标记 | 暂不展示，改用安全提示或转人工 |
| 分数偏高但未标记 | 记录日志，进入抽样复查 |
| 审核返回错误 | 使用保守策略，不把失败当作通过 |

## 不要把它当成一次性开关

真正容易出问题的地方，是把审核分数写成固定阈值后长期不管。

官方文档提到，OpenAI 会持续升级 moderation endpoint 底层模型。如果你的自定义策略依赖 `category_scores`，后面可能需要重新校准。这个提醒很关键。

也就是说，今天的 0.62 和下个月的 0.62 不一定意味着完全相同的业务风险。比较稳妥的做法是保存一段时间的样本：用户输入、模型输出、审核类别、分数、最后的产品动作，以及人工复核结果。

然后每隔一段时间检查三件事：

1. 被拦截的内容里，有多少其实可以放行。
2. 被放行的内容里，有多少后来被投诉或人工判定有问题。
3. 不同类别的阈值是否应该分开设置。

比如社区产品可能对骚扰类内容更敏感，教育产品可能更关注自伤、危险行为和未成年人相关内容。一个统一阈值通常不够精细。

## 对开发者的一个现实提醒

这次更新还有一个细节：流式生成时，审核分数会在完整输出可用之后到达，不会随着每个 partial delta 一起返回。

这会影响前端体验。如果你的产品边生成边展示，就不能假设“用户看到的每一段文字都已经审核过”。更保守的方案是对高风险场景先缓冲输出，等完整审核结果回来后再展示；对低风险场景可以继续流式展示，但在后端保留输出审核和事后处理能力。

还有工具调用场景。文档说明，审核会覆盖对话内容里的 tool-call arguments 和 tool outputs，但不覆盖工具名称、工具描述、工具 schema 或 response-format schema。做 agent 产品时，这意味着你仍然需要对工具权限、参数校验和外部系统返回值保持独立控制。

## 今天该做的不是“接入”，而是重新画流程

如果你的 AI 产品已经有内容安全逻辑，可以先不用急着改代码。更值得做的是把现有流程画出来：

- 哪一步审核用户输入？
- 哪一步审核模型输出？
- 哪些内容直接拦截？
- 哪些内容进人工复核？
- 审核服务失败时怎么处理？
- 日志里有没有保留足够的信息，方便以后调策略？

如果画完发现所有判断都挤在“展示前最后一秒”，那这次 moderation scores 正好提供了一个重新设计的机会。

AI 应用不会只靠更强模型取胜。真正能长期跑起来的产品，还要能解释自己为什么拦、为什么放、为什么转人工。

这条 OpenAI API 更新的价值就在这里：它把安全信号从外围服务拉回到了生成链路里，让产品团队有机会把安全做成正常流程的一部分，而不是上线前才加上的附加检查。
