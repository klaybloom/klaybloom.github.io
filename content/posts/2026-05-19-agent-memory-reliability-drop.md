过去一年，很多 AI Agent 产品都在讲“长期记忆”。

听起来很顺：用户做过什么、系统踩过什么问题、上次怎么解决的，都写进记忆。下次遇到类似任务，Agent 读一下自己的经验，就能越用越聪明。

但 5 月 18 日的 AIHOT 日报里，有一条论文研究很值得所有做 Agent、知识库、个人 AI 助手的人停下来看看：**记忆并不一定越更新越好。**

论文标题是 [Useful Memories Become Faulty When Continuously Updated by LLMs](https://arxiv.org/abs/2605.12978)。作者做了一组实验，结论很直接：当 LLM 反复把自己的经历压缩成“经验总结”，再不断改写这些总结时，记忆会慢慢失真，甚至让模型表现低于没有记忆的时候。

最刺眼的数字是这个：

**在一组 ARC-AGI 任务里，GPT-5.4 原本不带记忆可以做到 100% 正确；把这些题的标准答案喂进记忆整合流程后，再做同一批题，正确率掉到 54%。**

这不是“数据太脏”。论文强调，模型看到的是正确轨迹和标准答案。问题出在后面的动作：把经历压缩成一段可复用的文字记忆。

## 发生了什么

现在很多 Agent 记忆系统的默认流程是：

1. Agent 完成一个任务。
2. LLM 把完整过程总结成一条经验。
3. 这条经验被写进长期记忆。
4. 后续任务来了，再检索这些经验。
5. 新经验继续改写旧经验。

这个流程很有吸引力，因为它便宜、简单、容易接到现有 RAG 系统里。产品上也很好讲：用户越用，Agent 越懂你。

问题是，论文发现这种“持续重写”的记忆并不可靠。它会出现三类问题。

第一类是错误分组。不同任务的经验被放到同一个抽象规则里，最后变成一条看似合理、实际混杂的经验。

第二类是过度泛化。某个经验本来只适用于一个小场景，被总结后变成“通用建议”，后续任务就会被误导。

第三类是过拟合。记忆越来越像某几个样例的描述，遇到相邻但不完全相同的问题，反而更容易错。

![记忆失真机制](/images/posts/2026-05-19-agent-memory-reliability-drop/image-01.png)

论文项目页里还有一个很典型的现象：WebShop 实验中，某种记忆方案在 8 个样例时得分 0.64，但扩到 128 个样例后降到 0.20，回到了无记忆基线附近。ScienceWorld 里，把当前任务单独整理的记忆，比把所有历史任务混在一起持续整理的记忆高出 203 分。

这些数字指向同一个产品事实：**长期记忆不是“把历史总结得更短”，而是“在需要时拿回可靠证据”。**

## 这对 Agent 产品意味着什么

如果你在做 AI 助手、企业知识库、代码 Agent、客服 Agent，最危险的不是“没有记忆”，而是“记忆看起来很像真的”。

一条错误总结很容易给人安全感。它语言完整、条理清楚，还像是从历史经验里提炼出来的。但如果它已经丢掉了适用条件，Agent 后面每次检索它，都会把错误放大。

这也是很多 Agent 产品从 Demo 到生产会变脆的原因之一。

Demo 里，任务少、路径短、记忆也少，摘要看起来够用。到了真实用户环境，任务类型变多，历史记录变长，多个主题混在一起，持续摘要就开始把细节磨掉。

用户最后看到的是：Agent 好像记得我，但又经常记错我。

## 如果你正在做 Agent 产品

![可靠 Agent 记忆架构](/images/posts/2026-05-19-agent-memory-reliability-drop/image-02.png)

这篇论文给出的启发，不是“不要做记忆”，而是记忆系统要换一种设计。

第一，原始经历要作为一等数据保存。

不要只保存 LLM 写出来的经验总结。至少要保留关键任务的原始轨迹、输入、输出、工具调用、用户确认和失败记录。摘要可以存在，但它不应该替代证据。

第二，摘要要有触发条件。

不是每次任务结束都自动重写长期记忆。更合理的做法是：先判断这个经验是否稳定、是否跨任务复用、是否和已有记忆冲突，再决定是否进入长期摘要。

第三，检索结果要能回到来源。

Agent 给出某个建议时，不只返回一条“记忆笔记”，还要能返回它来自哪些原始记录。这样产品才能解释、调试和纠错。

第四，把删除和保留当成产品能力。

很多记忆系统只强调“记住更多”。但论文里的对照实验显示，只保留原始经历并选择性删除，也能接近甚至超过持续摘要方案。对产品来说，记忆管理不只是新增，还包括过期、隔离、撤回和审计。

第五，给用户可见的记忆控制权。

个人 AI 助手尤其需要这一点。用户应该能看到系统记住了什么、为什么记住、来自哪次互动，并且能删除或修正。否则“长期记忆”会变成一个黑箱。

## 真正的竞争点在记忆工程

模型能力还在涨，但 Agent 产品的差距不会只来自模型。很多时候，差距会来自状态管理、上下文组织、工具权限、记忆结构和失败恢复。

这篇论文把一个常见误区讲清楚了：LLM 很会写总结，但“会写总结”不等于“能维护可靠记忆”。

对创业者来说，这意味着长期记忆不是一个营销功能，而是一套基础设施。

对开发者来说，这意味着不要把 `summarize(history)` 当成记忆系统。

对产品人来说，这意味着记忆体验要能被用户理解和纠错，而不是只在设置页里放一个“开启长期记忆”的开关。

今天最值得带走的一句话是：

**可靠的 Agent 记忆，应该先保存证据，再选择性生成摘要。顺序反了，越聪明的总结，越可能把系统带偏。**
