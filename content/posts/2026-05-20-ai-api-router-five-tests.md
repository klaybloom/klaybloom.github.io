很多团队接入大模型 API 时，第一反应是比价格。

同样是 OpenAI-compatible 接口，谁更便宜，谁支持的模型更多，谁的充值门槛低，就先试谁。对个人开发者和小团队来说，这个选择很现实：模型调用一天几百次还好，一旦产品有真实用户，token 费用很快会变成固定成本。

但 2026 年 5 月 19 日的 AIHOT 日报里，有一条工具更新值得认真看：开源项目 `api-relay-audit` 把第三方 AI API 中转站的风险做成了可运行的审计流程。它检查的不是“能不能返回答案”，而是中转链路有没有做不该做的事。

这件事对创业团队尤其重要。因为一旦你把用户请求、系统提示词、工具调用和账单都交给中转站，风险就不再只是“模型慢一点”。它可能影响产品质量、用户数据、成本统计，甚至影响你对模型能力的判断。

## 中转站不是一根透明网线

理想状态下，中转站只做三件事：转发请求、返回响应、记录账单。

现实里，很多中转服务会加入自己的路由、限流、模型映射、缓存、错误处理和提示词处理。有些是为了兼容，有些是为了成本，有些只是工程质量不够好。

问题在于，调用方很难直接看见这些处理。

你以为发给了某个模型，实际可能被路由到另一个模型。你以为完整上下文已经送达，实际可能被截断。你以为工具调用参数原样经过，实际中间层可能改写了结构。你以为错误只会返回给你，实际错误响应里可能泄漏了内部信息。

![中转链路风险图](/images/posts/2026-05-20-ai-api-router-five-tests/image-01.webp)

`api-relay-audit` 的价值就在这里：它把这些隐性问题变成可检查的项目。根据项目 README，它覆盖 hidden prompt 注入、prompt 泄漏、指令覆盖、上下文截断、工具调用改写、错误响应泄漏、SSE 流异常，以及 Web3 场景下的钱包安全风险。工具可以在本地运行，输出结构化 Markdown 报告，并给出 `LOW / MEDIUM / HIGH` 的总体判断。

## 先测这 5 件事

如果你正在评估一个中转站，不建议只拿一句“你好”去测延迟。那只能证明接口活着，不能证明它可靠。

更实用的做法，是先看 5 个问题。

第一，请求有没有被加料。

中转层如果偷偷加入系统提示词，可能会改变模型行为。轻则回答风格变了，重则你的安全策略被覆盖。对客服、金融、代码生成这类场景，这不是小问题。

第二，提示词和密钥有没有泄漏迹象。

很多团队会把业务规则、用户信息、工具描述放进 prompt。中转站如果错误处理不当，日志、报错或调试信息里可能露出不该出现的内容。

第三，上下文有没有被截断。

有些中转服务为了节省成本，会对长上下文做截断或降级。调用方最容易误判：模型看似“理解错了”，其实是关键上下文根本没到模型那里。

第四，工具调用有没有被改写。

Agent 产品越来越依赖 function calling 和 tool use。中转层如果改变 schema、参数或返回结构，表面上只是一次调用失败，实际会破坏整个工作流。

第五，计费和输出是否可审计。

价格便宜没有问题，问题是账单、模型、token 统计和响应质量要能对得上。否则团队很难判断成本变化到底来自用户增长、模型切换，还是中间层行为变化。

## 采购前，把审计变成流程

这类工具不应该只在出事后使用。更适合放到三个时间点。

第一个时间点是供应商评估。接入前，对候选中转站跑一遍基础审计，报告留档。哪怕最后选择便宜方案，也要知道自己接受了哪些风险。

第二个时间点是上线前。把核心场景的系统提示词、长上下文、工具调用和错误处理都测一遍。不要只测闲聊，要测真实业务路径。

第三个时间点是持续复查。中转站的上游模型、路由策略和价格策略都可能变化。一次通过不代表长期可靠。

![采购审计清单](/images/posts/2026-05-20-ai-api-router-five-tests/image-02.webp)

对中文 AI 创业团队来说，这条新闻的提醒很直接：大模型基础设施已经不只是“选官方还是选中转”。真正要问的是：你有没有能力证明这条链路没有悄悄改变你的产品？

便宜可以用，但不能盲用。中转可以接，但要有审计。否则你省下来的 token 成本，可能会在用户信任、排障时间和错误决策里还回去。
