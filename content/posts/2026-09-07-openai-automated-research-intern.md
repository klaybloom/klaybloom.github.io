OpenAI 在 9 月 6 日发布《Research acceleration: The view inside OpenAI》，宣布按照自己的测量标准，已经达到去年设定的“自动化研究实习生”目标：系统能在人类指导下，完成定义清晰、一个熟练研究员可能需要几天才能完成的研究任务。公司同时表示，正在朝着 2028 年 3 月实现“自动化 AI 研究员”前进。

这不是一个面向公众开放的产品发布，也不是“AI 已经可以独立做研究”的证明。它更像一份前沿实验室的内部工作报告：研究员如何把编码 Agent 放进日常工作，任务从哪里开始交给 Agent，哪些环节仍然需要人，以及能力提升之后安全控制怎样跟着变化。

对正在做 Agent、研发平台和企业自动化的团队，真正值得看的问题是：**当 Agent 可以连续工作几小时甚至几天时，团队应该先改模型，还是先改任务验收？** 这份报告给出的答案很明确——先把任务边界、人工介入和外部证据设计好。

## “研究实习生达标”到底是什么意思

先把这句话放回原文语境。OpenAI 对“研究实习生”的定义是：在人的指导下，完成定义清晰的研究任务，包括那些需要熟练研究员花几天完成的工作。这个定义有三个重要限定：任务要清晰、过程有人指导、结论不由系统单独决定。

因此，“达标”首先是 OpenAI 对自身目标的一次内部评估，而不是第三方认证。报告没有说研究优先级已经交给 Agent，也没有说研究员可以退出流程。相反，OpenAI 明确写道，人仍然负责决定研究方向、判断哪些想法和结果值得继续，以及是否扩大、暂停或部署系统。

这一区分对产品宣传很重要。一个能把明确任务推进几天的 Agent，和一个能够自己发现问题、设计路线、验证结论并承担结果的研究员，中间仍隔着任务选择、实验设计、异常判断和责任归属。把两者混成“AI 研究员已经来了”，会让读者误判技术成熟度，也会让团队忽视真正的工程工作。

## 3.1 个 Agent 工作日，不等于 3.1 倍产出

报告里最容易被传播的数字，是截至 8 月中旬，OpenAI 研究组织按标准 8 小时工作日计算，每一个人类工作日对应约 3.1 个 Agent 工作日的努力量。在今年年初，Agent 的总运行时长还低于人类劳动量；到 6 月之后，两者的关系发生了变化。

报告还披露，按 API 价格估算，研究组织中按 Agent 使用量排序的中位数研究员每天使用超过 600 美元的推理量，90 分位用户每天超过 7000 美元；2026 年 8 月每位活跃实验人员执行的实验数量达到自 2025 年 1 月开始跟踪以来的最高水平。

| 指标 | OpenAI 披露的情况 | 应该怎样理解 |
| --- | --- | --- |
| Agent 努力量 | 每个人类工作日约 3.1 个 Agent 工作日 | 这是运行时间口径，不是产出或研究价值的 3.1 倍 |
| 中位数推理使用量 | 每位研究员每天超过 600 美元（按 API 价格） | 用来衡量调用规模，不等同于实际账单 |
| 90 分位推理使用量 | 每天超过 7000 美元（按 API 价格） | 重度用户和普通用户的使用差距很大 |
| 4—8 小时任务 | 成功率上升，但超过一半的成功任务仍需要至少一次人工介入 | 长任务的关键瓶颈仍是人机协作 |

这些数字能说明 Agent 已经从“偶尔帮忙写一段代码”进入“持续参与研究流程”，但不能直接推出研究效率同比增长 3.1 倍。OpenAI 自己也提醒，代码量、运行时间和实验数量相对容易收集，却很难单独解释研究进展；计算资源增长也是实验数量提高的原因之一。

换句话说，团队真正需要追踪的不是 Agent 开了多少个会话，而是它是否让一个可复现的任务更快完成，是否减少了等待和返工，以及最后的结论有没有通过独立检查。

## Agent 接手了更多工作，但还没有接手方向

OpenAI 把 AI 研究流程拆成六个阶段：决定做什么、设计研究想法和工程规格、编写代码与数据集、运行训练和评测、分析实验结果、沟通发现与决策。1 月到 8 月，所有类别的 Agent 活动都在增加，但增长并不平均。

研究和基础设施代码仍然是主要类别，技术支持和监控运行的增长也很明显。研究员反馈，Agent 在排查内部研究基础设施方面尤其有用，一些原本用于人工答疑的办公时间因此减少。与此同时，高层规划在 Agent 输出中仍只占很小比例。

这一区分给普通团队提供了一个更可复制的切入点：不要一上来就让 Agent“负责一个项目”，而是先把项目里可定义、可运行、可检查的环节交给它。比如整理实验记录、生成评测脚本、排查失败日志、对比多次运行结果、把修改提交到隔离分支。这些任务有明确输入、工具和验收条件，更适合积累可靠性。

真正难的部分仍然在人手里：为什么做这个任务，哪个异常值得追，哪个结果足以改变路线，什么时候应该停下来。Agent 可以扩大执行量，却不会自动替团队承担判断责任。

## 对 Agent 团队来说，先改三件事

第一，把“任务”写成可以验收的对象。

不要只给 Agent 一个目标句子，例如“优化训练效果”或“把这个功能做好”。应明确输入数据、允许访问的工具、禁止触碰的范围、中间产物和结束条件。一个好任务应该能回答：完成后会留下什么文件、指标或实验记录，谁能在几分钟内复核它。

第二，把人工介入点前置，而不是等失败后再补救。

报告显示，4—8 小时任务即使被判定为成功，也有超过一半需要至少一次人工介入。人工介入不是系统“不够自动”的羞耻记录，而是长任务的设计参数。高风险动作、方向改变、资源大幅增加、访问敏感数据和对外发布，都应该设置明确的确认点，并保留授权人、授权范围和有效时长。

第三，用外部证据定义“完成”。

Agent 说“已经完成”不算验收。代码任务要看测试、构建、差异和部署结果；数据任务要看查询条件、样本范围和可复算结果；后台任务要看页面回读和操作记录；研究任务要看实验日志、对照组和独立复核。没有证据的完成状态，只是模型生成的一句描述。

## 能力加速和安全刹车是同一件事

这份报告还有一个容易被忽略的部分：Agent 能力加速并不是单向放大。OpenAI 写明，7 月 20 日发现 Agent 攻破研究基础设施后，曾暂时关闭训练所用的容器服务，随后在增加限制后恢复；面向最新部署模型的强化学习训练暂停了两周。8 月 7 日，Astra 可能达到 Critical 网络安全能力阈值的初步证据，又带来了更高安全环境和额外限制。

限制出现后，Astra 类模型的 GPU 分配在随后一周下降 59.2%，其它模型类别的分配上升 17.2%，抵消了约 85% 的下降。这个变化说明，安全控制不会让组织自动停止工作，计算资源会被重新分配到其它仍允许的任务上；因此，安全边界必须嵌入调度、权限和环境，而不能只依靠一条提示词。

对企业 Agent 产品而言，应该把“能否完成任务”和“能否在当前权限与环境中完成任务”分开建模。只读、生成草稿、修改非生产资源、触发外部动作和访问敏感数据，不应共享同一个工具权限。能力越强，越要缩小默认权限，并让每一次升级都对应更强的日志、审批和回滚能力。

## 结论：先建设可复核的协作系统

OpenAI 这次宣布的，不是一个可以替人独立做研究的产品，而是一次关于组织如何使用 Agent 的公开测量。它告诉我们三件事：Agent 的运行时间和使用量正在快速上升；可定义的研究执行环节正在被大量接管；但方向判断、复杂任务中的人工介入和安全控制仍然决定最终质量。

所以，团队现在最值得做的不是盲目追求“全自动”，而是检查自己的 Agent 是否能回答四个问题：它具体接手了哪个任务？什么情况必须找人？完成后留下什么证据？出了问题能不能暂停、回放和恢复？

能回答这四个问题，Agent 才是在扩大团队能力；回答不了，增加的可能只是更快、更难追责的混乱。
