这两年做 AI 产品，最容易被低估的工作不是接 API，而是选模型。

同一个功能，换一个模型，成本可能差几倍；同一个模型，换一个供应商，价格、上下文窗口、工具调用、图片输入、缓存计费又会不一样。更麻烦的是，信息散在几十个官网、文档、定价页和更新公告里。团队开会时，经常不是在讨论产品本身，而是在互相问：这个模型现在到底多少钱？支持结构化输出吗？上下文窗口是多少？能不能看图？有没有推理能力？

AIHOT 2026-05-24 日报里提到的 [Models.dev](https://models.dev)，正好解决这个小而真实的问题。它不是又一个模型排行榜，而是一个开源的 AI 模型规格、价格和能力数据库。

## 它解决的不是资讯问题，而是决策问题

Models.dev 的价值不在于告诉你“哪个模型最强”，而是把选型时会反复查的字段放在同一张表里。

它当前通过公开 API 提供数据。今天检查时，`https://models.dev/api.json` 返回了 134 个 provider 和 4846 个模型条目，覆盖 OpenAI、Anthropic、Google、OpenRouter、Azure、SiliconFlow 等供应商或聚合平台。

每个模型条目不只写名字，还会记录这些字段：

| 字段 | 对产品团队的意义 |
| --- | --- |
| `cost` | 估算输入、输出、缓存、音频等费用 |
| `limit` | 判断上下文窗口和输出长度是否够用 |
| `modalities` | 判断是否支持图片、音频、PDF 等输入输出 |
| `tool_call` | 判断能否接工具和业务系统 |
| `structured_output` | 判断是否适合做稳定的数据抽取 |
| `reasoning` | 判断是否适合复杂推理任务 |
| `release_date` / `last_updated` | 判断模型是否新、数据是否近期维护 |

这对创业团队很实用。很多产品不是输在模型能力，而是输在早期估算太粗：Demo 用高价模型很顺，真实用户一上来，单用户成本压不住；客服、检索、代码、图片理解都塞给同一个模型，体验和费用一起失控。

## 更适合放进团队工作流

Models.dev 的另一个特点是它不是封闭网页。它的 README 明确给出 API：

```bash
curl https://models.dev/api.json
```

这意味着它可以进脚本、进后台配置、进 CI，也可以被内部工具读取。

例如，团队可以做三件事：

1. 在产品报价前，把候选模型的输入、输出、缓存价格拉出来，按真实调用量估算毛利。
2. 在工程方案里，用 `tool_call`、`structured_output`、`modalities` 过滤不适合的模型，避免后面返工。
3. 在模型更新时，把 `last_updated` 和成本字段放进监控，提醒团队重新评估默认模型。

这类数据库还适合产品经理和研发共用。产品经理可以用它理解“为什么这个功能要限制图片数量或输出长度”，研发可以用它把模型选择从个人经验变成可复查的配置。

## 开源这件事很关键

模型价格和能力变化太快，单个网站很难长期维护准确。Models.dev 选择把数据放在 [GitHub 仓库](https://github.com/sst/models.dev) 里，用 TOML 文件组织 provider 和 model，并通过 GitHub Action 做 schema 校验。

它的贡献方式也比较清楚：新增 provider、补充 logo、添加模型定义、提交 PR。模型字段需要满足 schema，成本、上下文、模态能力等信息都有固定位置。

这不是完美答案。价格页可能改，供应商可能调整计费项，聚合平台也可能出现同名模型不同限制的问题。所以它不能替代最终合同和官方文档。但作为第一层筛选，它已经比在浏览器里打开十几个标签高效很多。

## 适合怎么用

对中文 AI 创业者、开发者和产品人，我会建议把 Models.dev 当成三类工具使用。

第一类是“选型表”。当你要做客服、代码助手、知识库、图片理解、语音助手时，先拉候选模型，筛掉明显不支持所需能力的模型。

第二类是“成本表”。别只看输入输出价格，还要看缓存、推理、音频、图片等附加维度。AI 产品的利润，经常就藏在这些小字段里。

第三类是“更新提醒”。每周检查一次核心供应商和默认模型的变化。模型更新不一定意味着要马上换，但团队至少要知道还有哪些更便宜、更快或能力更合适的选择。

## 最后

AI 行业每天都有新模型、新榜单、新融资，但真正影响团队现金流和交付质量的，往往是这些朴素的基础设施。

Models.dev 值得关注，不是因为它声音大，而是因为它把一个重复、琐碎、容易出错的工作变成了可以查询、可以提交 PR、可以接入系统的数据源。

如果你的团队已经有固定模型清单，可以把它拿来做一次对照：价格有没有变，能力字段有没有漏，上下文窗口是否还满足当前产品。这个动作不复杂，但会让后面的产品决策少很多争论。
